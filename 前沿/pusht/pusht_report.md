# 机器人数据集作业：`lerobot/pusht` 选型与数据问题分析报告

> 数据来源：`https://hf-mirror.com/datasets/lerobot/pusht`
> 所有数值均由本组脚本实测获取，未直接抄录清单表格：结构类来自 `checkup.py`，数据类来自 `verify_data.py`（读取本地 `data/`、`meta/` 分片），曲线由 `plot_data.py` 绘制。
> 环境：Windows + Python，本地目录 `pusht/pusht/`（全部分片已下载）。

## 二、发现的实际问题（重点）

> 评分看重"从数据里发现并分析问题"，以下每条均附脚本实测证据、影响与处置建议。

### 问题 1：`next.success` 全为 False，数据集没有一条"成功"样本（最严重）

- 证据：脚本实测 `next.success` 的 True 个数 = **0**（25650 帧全为 False）；同时全库单条最高覆盖率 `next.reward` 仅 **0.9489 < 0.95**，**206/206 条**都没越过常见的 0.95 成功阈值。
- 影响：PushT 本应是"成功/失败"可区分的任务，但该字段**恒定无效**。凡是要按 `success` 过滤成功轨迹、或训练成功判别器的流程，都会得到空的成功集；直接拿它当标签会训出全负类分类器。
- 处置：不要使用 `next.success`；若需成功判定，改用末帧 `next.reward` 覆盖率自行设阈值（本报告采用 0.90 / 0.85 分层，见下）。

### 问题 2：`observation.state` 只有 2 维、不含 T 形方块位姿，观测不完整

- 证据（a）：全库 `corr(reward, state_x) = -0.109`、`corr(reward, state_y) = -0.005`，即任务进度（覆盖率）与 state 两维**几乎无关**。
- 证据（b）：把 state 平面切成 20×20 网格，格内 `next.reward` 标准差均值 **0.129**，而全局标准差 **0.278**——若 reward 由 state 决定，同一位置格内 reward 应几乎恒定，实测并非如此。说明 state 记录的是**推子（agent）位置**，而不是决定任务成败的**方块位姿**。
- 影响：state 不构成完整观测（非马尔可夫）。仅用 state 训练的"仅状态"基线拿不到完成任务所需信息，必须依赖图像；这也解释了问题 1 中"成功率"为何难以判定。
- 处置：做 state-only 基线时须预期其失败；状态侧至少补充方块位姿，或明确依赖 `observation.image`。

### 问题 3：图像统计被截样到 `min(长度, 100)`，与数值特征口径不一致

- 证据（a）：逐段 `stats/observation.image/count` **恰好等于 `min(episode 长度, 100)`**，206 条全部成立；长度 > 100 的 **152** 条被截样到 100。
- 证据（b）：图像 stats 合计 **19619 / 25650 = 76.5%** 帧；而 `stats/observation.state/count` **恰好等于长度**（覆盖全部帧）。
- 影响：图像归一化用的均值/方差只在约 **3/4 帧**（且长片段等距抽样）上估计，与数值特征的全量口径不一致；跨数据集对比或直接照搬该统计做归一化会带偏差。
- 处置：报告与复现时说明图像统计为抽样值；如需精确归一化，在全量帧上自行重算。

### 问题 4：`action` 被量化成整数像素，控制精度受限

- 证据：`action` 全部为整数（`np.allclose(action, round(action)) = True`），取值落在 **[12, 511]** 的整数网格；而 `observation.state` 为连续浮点（如 225.2524）。
- 影响：动作空间实际是 512×512 的离散格点（分辨率约 **0.2%** 画布），并非真连续；做连续动作的扩散/流匹配策略时，标签本身带 1px 量化噪声，与 state 的连续口径也不一致。
- 处置：训练前明确动作是"像素级离散"，或把量化误差纳入噪声建模；评估时以像素误差而非亚像素误差为基准。

### 问题 5：`next.done` 终止标记每段重复出现 2 次

- 证据：`next.done` 的 True 共 **412** 个 = **2 × 206**；逐段统计每段恰好 2 个，且都落在**末帧与倒数第 2 帧**（相对段尾偏移 {0, 1}）。
- 影响：终止信号被重复标注，按 `done` 切段/算回报会重复截断一次；若用 `done` 计算折扣回报，末两步会被多打一次终止。
- 处置：取"每段最后一个 done"作为真实终止；或在预处理中把重复的终止行去重。

### 问题 6：README 与实际的目录布局版本不一致

- 证据：仓库 `README.md` 内嵌的 `info.json` 仍写 `codebase_version = v2.0`、`data_path = data/chunk-{episode_chunk}/episode_{episode_index:06d}.parquet`、`total_videos = 206`；而实际的 `meta/info.json` 已是 **v3.0** 分块布局（`data/chunk-{chunk_index:03d}/file-{file_index:03d}.parquet`，单文件 1 个分片）。
- 影响：README 是自动生成的快照，迁移到 v3 后未同步。若按 README 的路径规则写加载代码会全部 404。
- 处置：一律以 `meta/info.json` 为准；加载器不要硬编码 README 里的路径模板。

### 问题 7：单任务、单视角，任务与语言多样性为零

- 证据：`total_tasks = 1`，`task_index` 全库取值只有 `[0]`，206 条 episode 的指令**完全相同**；相机只有 1 路 `observation.image`。
- 影响：无法做语言条件 / 多任务泛化 / 多视角消融；数据集只覆盖单一任务分布，泛化结论不可外推。
- 处置：作为单任务基准使用；需要语言条件实验时另选多任务数据集。

### 问题 8：相机分辨率低且采用 av1 编码

- 证据：`observation.image` 为 **96×96×3**、`codec = av1`、`pix_fmt = yuv420p`。
- 影响：96×96 已是低分辨率，av1 在部分老旧解码栈/浏览器上兼容性较差（本机用 OpenCV 可正常解码 25650 帧，但需确认训练环境支持）。
- 处置：确认解码后端支持 av1；如需放大输入，注意上采样不会增加真实信息量。

## 三、异常筛查（模块 2 判据与分层）

### 判据：不能直接套用 droid 的阈值

| 判据（来自 droid_100） | 在 pusht 上的实测 | 问题 |
|---|---|---|
| 硬伤：时长 < 1 s（10 帧） | **0** 条（最短 49 帧 = 4.9 s） | 无区分度 |
| 硬伤：移动量 < 中位数 5%（70.5 px） | **0** 条（最小 467.6 px） | 无区分度 |
| 存疑：时长 > 3× 中位（366 帧） | **0** 条（最长 246 帧） | 无区分度 |
| 存疑：停顿帧占比 > 50% | **0** 条（最大 7.4%） | 无区分度 |

> 结论：pusht 是**经过筛选的高质量演示集**——长度集中（CV=0.29，49~246 帧）、每段都有连续运动（无停顿帧）、无失败/超短样本。用 droid 的"时长/移动量/停顿"判据会得到**全 0**，必须换用与任务语义相关的判据。

### pusht 专用判据：按**终点覆盖率**（末帧 `next.reward`）分层

T 形装配是精密对齐任务，末帧覆盖率直接反映"是否把方块推到位"。据此分三层：

| 类别 | 判据 | 实测条数 | 占比 |
|---|---|---|---|
| 可以 | 终点覆盖率 ≥ 0.90（基本对上目标） | **90** | 43.7% |
| 存疑 | 0.85 ≤ 终点覆盖率 < 0.90（部分对齐） | **100** | 48.5% |
| 不行 | 终点覆盖率 < 0.85（明显没对位） | **16** | 7.8% |

**判定以终点覆盖率为主判据，时长仅作辅助标注（两者冲突时以覆盖率优先）。**
辅助观察：< 6 s（60 帧）**2** 条——ep182 覆盖率 0.895 归"存疑"、ep205 覆盖率 0.825 归"不行"；> 20 s（200 帧）**5** 条——其中 **3** 条覆盖率仍 ≥ 0.90（ep54 / ep174 / ep190 归"可以"）、**2** 条归"存疑"（ep123 / ep184）。pusht 无停顿帧（最大停顿占比 7.4%），停顿判据不适用。

### 三类判定示例（可以 / 存疑 / 不行 各 2 条）

![](three_class_curve.png)

> 图 4　三类样本的 state（实线）/ action（虚线）2 维时序 + 覆盖率（右轴灰点线，本地实测）；各类取**类内覆盖率中位附近**的代表样本，避免拿类内极值代表整类。

| 类别 | episode | 帧数 / 时长 | 终点覆盖率 | 说明 |
|---|---|---|---|---|
| 可以 | 33 | 120 / 12.0 s | **0.911** | 覆盖率 = 可以类中位（该类 90 条，0.900~0.949），该类典型样本 |
| 可以 | 160 | 147 / 14.7 s | 0.911 | 同为类内中位附近的常规长度样本，无停顿帧 |
| 存疑 | 90 | 109 / 10.9 s | 0.885 | 覆盖率 = 存疑类中位（该类 100 条，0.85~0.90），"推了大半、没完全对位" |
| 存疑 | 178 | 148 / 14.8 s | 0.885 | 时长与全库中位相当，属"完成度差一口气"而非偏长 |
| 不行 | 45 | 152 / 15.2 s | 0.832 | 覆盖率接近不行类中位 0.835（该类 16 条，0.813~0.848），未达标 |
| 不行 | 113 | 149 / 14.9 s | 0.838 | 同上；轨迹连续、时长正常，并非坏帧 |

> 说明：可以类覆盖率最高的是 ep32 / ep124（0.949 / 0.948），不行类最低的是 ep153 / ep95（0.813 / 0.813），但它们是**类内极值、不具代表性**，故代表样本统一改取各类中位附近；其中 ep32 已单独用于 §四 曲线解读。
> 另需注意：不行类的移动量中位 **1614.3** 反而**大于**可以类的 **1427.4**，"动作幅度"在本数据集上无法区分好坏——判据只能是终点覆盖率。

**结论**：可以类（90 条，覆盖率 ≥ 0.90）可直接用于模仿学习；不行类（16 条，< 0.85）**不宜作成功示范**，但轨迹连续、时长正常，作负样本或降权样本仍可保留；存疑类（100 条，0.85~0.90）完成度差一口气，按要求筛选后再用。

## 四、曲线解读（模块 3，选定 episode：32，148 帧，14.8 s）

![](ep32_curve.png)

> 图 1　episode 32 的 state / action 2 维时序（上）与覆盖率、推子平面轨迹（下）

**现象**：该段 0～14.8 s，state（推子位置）两维平滑推进；action（目标指令）紧随 state 但始终**领先**一截；`next.reward`（覆盖率）从 0.000 单调升到 0.949，同段内 `corr(时间, 覆盖率) = 0.909`。但把全库放在一起看，覆盖率与 state 的位置**几乎不相关**（`corr(reward, state_x) = -0.109`）。

**猜测**：`observation.state` 记录的是**推子（agent）自身位置**，而不是被推的**方块位姿**；任务进度由方块与目标的重合度决定，所以覆盖率随时间上升、却与推子所在位置无关。

**验证办法**：
1. 在全库层面计算 `next.reward` 与 `state` 两维的皮尔逊相关系数；
2. 把 state 平面切成 20×20 网格，检查**同一格内 reward 是否稳定**（若 state 是方块位姿，reward 应是 state 的函数）；
3. 计算同一 episode 内 `时间` 与 `覆盖率` 的相关，确认覆盖率是"任务进度"而非位置函数；
4. 计算 `action[t]` 与 `state[t+1]` 的相关，确认 action 是"下一步目标位置"。

**验证结果（脚本实测）**：
- `corr(reward, state_x) = -0.109`、`corr(reward, state_y) = -0.005`（近 0）；
- state 平面 20×20 分格，**格内 reward 标准差均值 0.129** vs 全局 0.278，reward 并非 state 的函数；
- 同段内 `corr(时间, 覆盖率) = 0.909`（全库均值 0.802），覆盖率随进度升高；
- `corr(action[t], state[t+1]) = 0.986 / 0.985`（两维），帧内 `|action − state|` 均值 **29.5 px**——action 确实是"领先一步的目标位置"。

**判断**：☑ 不能（仅以 state 为观测）　□ 能用　□ 不确定

**理由**：state 只含推子位置、不含方块位姿，奖励与 state 近乎无关，说明**仅凭 state 无法判断任务是否完成**，观测不完整；训练与评估都必须以 `observation.image` 为主，state-only 基线不可用。

## 五、结合任务给出的分析角度

| 分析角度 | 本数据集可落地的做法 |
|---|---|
| 相机视觉 / 去视觉对比 | 仅 1 路 96×96 相机，可做"图像+state vs 仅 state"消融；结合问题 2 预期仅 state 会失败 |
| 状态/动作维度差异 | state 连续浮点 2 维、action 整数像素 2 维；结合问题 4 分析量化误差对连续策略的影响 |
| 低帧率/异常帧率 | 10 fps 正常；结合问题 3 的图像抽样，注意帧率不齐不会发生但统计口径不齐 |
| 脚本生成 vs 人机演示 | PushT 为人类演示（Diffusion Policy 原始数据），可与脚本生成数据对比 |
| 语言条件 / 关键点 | 结合问题 7：单任务单指令，无法做语言条件实验，只能作单任务基准 |
| 奖励/成功信号 | 结合问题 1/2：`next.success` 无效、`next.reward` 覆盖率与 state 无关，成功判定需从图像侧重建 |

## 六、结论

`lerobot/pusht` 满足全部 4 条硬门槛与 3 条偏好条件（v3 布局、单分片、206 episode、带 1 路视频，仅 7.3 MB），**判定为"可直接用"**，适合作为本次作业数据集。

数据本身存在多处**可分析的实际问题**：`next.success` 全为 False 且最高覆盖率 0.9489 未达 0.95 阈值（无成功样本）、state 只有 2 维不含方块位姿导致观测不完整、图像统计被截样到 `min(长度,100)` 只覆盖 76.5% 帧、action 被量化成整数像素、`next.done` 终止标记每段重复 2 次、README 与实际布局版本不一致、单任务单视角无多样性、96×96 低分辨率 av1 编码。这些正是本作业"发现并分析问题"的核心素材。

**总体判断（模块 4）：☑ 有条件地能**
- 模块 1：数据集含 206 条 episode、单路相机与 2 维状态/动作，规模与格式满足模仿学习训练条件；
- 模块 2：长度/移动量/停顿判据下无硬伤，但按完成度分层，**16 条"不行"需剔除、100 条"存疑"需筛选**，且 `next.success` 不可用；
- 模块 3：state 不含方块位姿、与奖励近乎无关，**必须依赖图像**，state-only 基线不可用；action 带 1px 量化误差。
- 即：原始数据不能"无脑"直用，需清洗判据 + 以图像为主 + 处理量化误差后才可用于训练。

建议后续步骤：已用 `verify_data.py` 跑通最小加载/统计，`plot_data.py` 复现全部曲线，上述 8 条问题均可在本地分片上复现。
