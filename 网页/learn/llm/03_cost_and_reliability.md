## 必答问题：为什么重试要加随机抖动（jitter）？

**因为不加抖动，所有客户端会同步成一个节拍器，把"暂时繁忙"放大成"永久繁忙"。**

推演一遍：1000 个客户端同时收到 429，都按"等 1 秒再试"：

```
t=0.0s  1000 个请求 → 服务端扛不住 → 全部 429
t=1.0s  1000 个请求**同时**涌来 → 服务端再次扛不住 → 全部 429
t=3.0s  1000 个请求**同时**涌来 → 又 429
        ...周期性尖峰，服务端永远缓不过来
```

每次重试都在**同一时刻**到达，服务端在"空闲"和"被淹没"之间反复横跳，
本来只是短暂限流，被重试策略变成了持续过载。

加抖动之后，每个客户端的等待时间被随机打散：

```
客户端 A: 1.0s   客户端 B: 0.6s   客户端 C: 1.4s   客户端 D: 0.8s
→ 请求被摊平到 [0.5s, 1.5s] 这个区间里，形成平滑流量
```

本项目的实现是**乘法抖动**（`compute_delay`）：延迟在 `[delay×(1-j), delay×(1+j)]`
内均匀取值，`j=0.5`。

> **为什么是乘法而不是"加减固定值"**：乘法保持相对比例 ——
> 基数 0.5s 时抖 ±0.25s，基数 8s 时抖 ±4s，两者都恰到好处。
> 加法抖动要么对小延迟过猛（±0.5s 让 0.5s 变成 0 或 1s），要么对大延迟毫无作用。

还踩到一个细节：**抖动不能把延迟压到 0**。代码里加了 `max(delay, 0.05)` 下限，
否则运气不好时会立刻重试，等于没退避。

## 1. Token 计量：tiktoken 能不能用来估成本？

**不能直接用，尤其对中文。** 实测（`cl100k_base` 词表 vs 网关真实 `usage`）：

| 文本类型 | 字符数 | tiktoken 估算 | 真实 prompt token | 偏差倍数 | 密度（tok/字） |
| --- | ---: | ---: | ---: | ---: | ---: |
| **中文** | 176 | 177 | 119 | **1.487** | 0.676 |
| 英文 | 395 | 108 | 120 | 0.900 | 0.304 |
| 代码 | 367 | 93 | 105 | 0.886 | 0.286 |

读法：

- **中文：tiktoken 高估 49%**。按它算成本会**偏贵**。原因是 `cl100k_base` 对中文
  的分词粒度比国产模型细 —— 常见中文词被切成更多 token。
  反过来看，**真实中文的 token 密度是 0.676 tok/字**，即**约 1.5 个汉字/token**。
- **英文/代码：低估约 10–11%**。这个方向更危险（按它算成本会偏便宜），
  但幅度不大，且部分是 message 封装开销（role 等固定约 10 token）造成的，
  真按正文比对时偏差更小。
- **代码和英文密度接近**（0.286 / 0.304 tok/字）：说明对这两类，
  "字符数 ÷ 3.5 ≈ token 数"是个可用的心算公式。

### 工程结论

1. **要精确成本，只能用网关返回的真实 `usage`**，不能靠 tiktoken 推算。
2. 需要**事前预估**（比如评估一个 10 万字的批量任务要多少钱）时，
   用**密度系数**而不是 tiktoken：中文按 `字数 × 0.68`，英文/代码按 `字符数 × 0.30`。
   这个系数是从实测来的，比拿 GPT 词表去套准得多。
3. **换模型必须重测密度**。不同厂商分词器差异巨大，1.5 倍偏差很常见。

### 一个容易漏的计费项：推理 token

早前观察到网关响应里有 `completion_tokens_details.reasoning_tokens`，
直觉是"思维链会被计费"。但**多做几次测量后发现结论不稳**：

| 配置 | completion_tokens（5 次） | 均值 | 可见 content 字数 |
| --- | --- | ---: | --- |
| `reasoning_effort="none"` | 270, 223, 285, 279, 153 | **242** | 287–519 |
| 不传（默认） | 93, 197, 259, 273, 233 | **211** | 172–465 |

**两种配置的 token 消耗在统计上没有区别，且方差比差异还大。**
所以诚实的结论是：

> **没能证明 `reasoning_effort="none"` 真的关闭了推理。**
> 本机网关接受这个参数，但 token 用量没有可测量地下降。
> 它可能只是被忽略，也可能推理 token 本来就计入 `completion_tokens` 而不单独暴露。

**这对成本表的影响**：不能假设"关掉推理能省钱"。如果换成明确支持推理开关的供应商，
必须**重新实测**，不要照搬这里的结论。

（第一次测时看到"关推理 completion=55 而开推理=49"，一度以为搞反了 ——
那只是单次样本的噪声。**单次测量在小样本上会给出完全相反的结论**，
这类判断至少要 5 次以上。）

## 2. 成本表：含重试的期望成本

`scripts/cost.py` 的输出（单价：输入 2 元 / 输出 8 元每百万 token，**示例锚点**）。

### 单次成本

| 场景 | 输入 tok | 输出 tok | 单次成本 | 输入占比 |
| --- | ---: | ---: | ---: | ---: |
| 短文本（22 字 / 2 字段） | 171 | 27 | 0.000558 元 | 61% |
| 标准合同（109 字 / 4 字段） | 227 | 89 | 0.001166 元 | 39% |
| 长合同（2,636 字 / 6 字段） | 1,918 | 78 | 0.004460 元 | 86% |

### 含重试的期望成本（p=0.95，最多 3 次）

期望尝试次数不是 1/p，而是**带上限的几何分布求和**：

$$\text{期望次数} = \sum_{k=0}^{N-1}(1-p)^k$$

`p=0.95, N=3` → `1 + 0.05 + 0.0025 = **1.0525**` 次，溢价 **5.2%**。

> **为什么不用 1/p**：`1/p` 是"无限重试"的期望。我们有 `max_attempts=3`，
> 已经放弃的情况下不该再计入"还会继续试"的成本 —— 那会高估。

| 场景 | 期望成本/次 | 每 1,000 次 | 每 10,000 次 | 最坏延迟 |
| --- | ---: | ---: | ---: | ---: |
| 短文本 | 0.000587 元 | 0.59 元 | 5.87 元 | 9,000 ms |
| 标准合同 | 0.001227 元 | 1.23 元 | 12.27 元 | 9,000 ms |
| 长合同 | 0.004694 元 | 4.69 元 | 46.94 元 | 9,000 ms |

### 成功率对成本的影响（这条最有用）

| 成功率 p | 期望尝试次数 | 每万次成本 | 相对 p=1.0 溢价 |
| ---: | ---: | ---: | ---: |
| 1.00 | 1.0000 | 11.66 元 | 0.0% |
| 0.99 | 1.0101 | 11.78 元 | 1.0% |
| 0.95 | 1.0525 | 12.27 元 | 5.2% |
| 0.90 | 1.1100 | 12.94 元 | 11.0% |
| 0.80 | 1.2400 | 14.46 元 | 24.0% |
| 0.50 | 1.7500 | 20.41 元 | 75.0% |

**决策依据**：成功率从 0.95 掉到 0.80，成本涨 18 个百分点。
这说明**可靠性投入是有账算的** —— 把成功率从 0.9 提到 0.95，
省下的钱可能还不够付重试层的开发成本，但能省下**用户的等待**（最坏 9 秒）。
成本从来不是唯一目标。

### 成本结构：输出比输入更贵

看"输入占比"这一列：标准合同的输入 token 更多（227 > 89），
但输入只占成本的 **39%** —— 因为输出单价是输入的 4 倍。

**所以"少让模型说话"（缩短输出）往往比"少喂正文"更省钱**，
除非正文特别长（长合同那行输入占 86%，因为 prompt 全是正文）。

## 3. 重试策略：4xx 一次都不重试

`app/core/llm/retry.py` 的核心判定：

| 情况 | 重试? | 理由 |
| --- | --- | --- |
| `429` 限流 | **是** | "现在忙"，等一会儿就好 |
| `5xx` | **是** | 服务端临时故障 |
| 超时 / 连接错误 | **是** | 网络抖动 |
| `400/401/403/404/422` | **否** | 请求本身错了，重试只是重复买同一个错误 |

**4xx 不重试是最重要的一条**：凭证错了重试 5 次，只会让你多花 5 次钱买到同一个 401，
并且把"key 配错了"这个真问题藏在"偶发失败"的表象里。

实测（`drill_retry.py` 场景 C，假 key 打真网关）：

```
WARNING 401-drill 第 1 次失败且不可重试（AuthenticationError），直接抛出
→ 退避次数：0（应为 0）
→ 总耗时：0.00s
```

对比场景 A（端口不通）：

```
WARNING 第 1/3 次失败（APIConnectionError），0.45s 后重试（含抖动）
WARNING 第 2/3 次失败（APIConnectionError），0.79s 后重试（含抖动）
→ 尝试 3 次，总耗时 7.39s
```

### 顺带发现的一个时序差异

场景 A（`127.0.0.1:9` 端口不通）耗时 7.39s，场景 B（`.invalid` 域名不存在）只 1.10s。

原因是：**端口不通要等满 `timeout`（3s×3≈9s），而 DNS 解析失败会立即返回**。
同样是 `APIConnectionError`，等待时间差 7 倍。

**这条对容量规划有意义**：如果依赖端点配置有误，每个请求会挂满超时，
并发数会迅速被这些"等着的请求"占满。所以 `timeout` 必须设得比想象中更保守。

## 4. 多 key 轮换 + 简单熔断

目的不是"恢复服务"，而是**止血**：key 被封/配额耗尽时，
继续用它重试只会让失败堆积，还拖慢所有请求（每个都要等超时）。

实现是三件事：
1. 轮转挑选可用 key
2. 连续失败 `threshold` 次 → 冷却 `cooldown` 秒
3. **401 这类不可重试的失败立即熔断**（key 本身废了，等连续 N 次是浪费）

实测演练：

```
初始可用： ['ke…-A', 'ke…-B', 'ke…-C']
B 失败 2 次 → 可用 2 个（B 已熔断）
连续挑选 4 次：['ke…-A', 'ke…-C', 'ke…-A', 'ke…-C']     ← B 被排除
C 遇到 401（不可重试）→ 立即熔断：True
全部熔断 → 抛 RetryExhaustedError：所有 key 都在冷却中
```

**最后一个行为是刻意的**：全部熔断时明确报错，而不是硬选一个必然失败的 key
再重试几轮。**快速失败 > 慢慢失败**。

### 演练中发现并修掉的一个 bug

第一版 `masked()` 规则是"长度 ≤ 12 就显示 `***`"，
演练时用了 `key-A` / `key-B` / `key-C` 这种短 key → **三条熔断日志长得一模一样**，
完全看不出是哪个 key 被熔断了，而这恰恰是排查熔断的唯一线索。

改成：长度 ≥ 12 保留前 6 后 4；长度 ≥ 4 保留前 2 后 2；更短才整体打码。
现在日志里是 `ke…-A` / `ke…-B` / `ke…-C`，可分辨且不泄露。

## 5. 测试：为什么不用 respx（实测踩坑）

验收要求是"用 respx 模拟 429→200"。**实测发现 respx 对 openai SDK 完全无效**：

```
openai 3.37.0
httpx  : 0.28.1
httpx2 : 2.16.0
httpx2 is httpx → False        ← SDK 内部用的是 httpx2（独立分叉）
respx 只 patch httpx           → 一条路由都拦不到
```

第一版测试用 `@respx.mock`，结果请求真实打到了网络（然后失败）。
**这是版本生态问题，不是用法错误。**

改用 SDK 官方支持的 `http_client=` 注入 `httpx2.MockTransport`：
直接替换传输层，绕开版本差异，也不污染全局。

核心验收断言：

```python
async def test_429_then_200_retries_exactly_once():
    recorder = _Recorder([Response(429), Response(200)])
    ...
    assert text == "ok"
    assert recorder.call_count == 2      # ← 1 失败 + 1 重试，不多不少
    assert len(policy.delays) == 1       # ← 只退避一次
```

还有一条同样重要：

```python
async def test_401_is_not_retried():
    assert recorder.call_count == 1      # ← 一次都不重试
    assert policy.delays == []           # ← 没有任何退避
```

## 6. 回扣：这些防线如何咬合

今天做的四件事其实是一条链：

```
                    ┌─ 4xx? ──→ 立即失败（不烧钱）
失败 ──┬─ 可重试? ─┤
       │            └─ 是 ──→ 退避+抖动重试 ──→ 仍失败?
       │                                            │
       └─ 否 ─────────────────────────────────────────┤
                                                     ▼
                                        LlmExtractor 降级到规则版
                                        （不 500，用户拿到结果）
```

三层各管一段、互不替代：

| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| `retry.py` | 瞬时故障（429/5xx/超时） | 4xx、业务错误 |
| `KeyRotator` | 单个 key 报废 | 全网关故障 |
| `LlmExtractor` 降级 | 模型这条路彻底不通 | 数据质量问题 |

**真实故障的形态常常出乎意料**：周三遇到过网关整体 502，
那时重试和熔断都救不了，只有降级层给出了结果。
所以**防线必须分层，不能指望任何单点**。

## 7. 给后续的检查清单

- [ ] 成本估算用**密度系数**（中文 0.68 tok/字、英文/代码 0.30 tok/字符），不要用 tiktoken
- [ ] 换模型必须**重测 token 密度**，1.5 倍偏差很常见
- [ ] 算成本必须**分开输入/输出**，输出通常贵 3–5 倍
- [ ] 期望成本用带 `max_attempts` 上限的公式，不是 `1/p`
- [ ] 4xx **绝不重试**
- [ ] 重试必须带抖动，且延迟不能抖到 0
- [ ] `timeout` 要保守：端点不通时每个请求都会挂满超时
- [ ] 短 key 的掩码要能分辨，否则熔断日志失去意义
- [ ] 用 `httpx2.MockTransport` 而不是 respx 测 SDK 请求
